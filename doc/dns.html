DNS tunnel

JSON type dns. Local TCP is carried as DNS queries for long names under a domain you control. The default query type is TXT. A client can set qtype to aaaa or a instead. The session is KCP, then Noise, then smux. One smux stream is one raw TCP connection to the tagged service. This is a PT Proxy session: a stock dnstt client or server cannot decode it. There is no DoH, no DoT, and no UDP associate. reverse-tag is not used.

Use cases

  • A network that still allows UDP/53 to a recursive resolver, including one that blocks every TCP connection.
  • Forward a tagged socks, http, or external service. The client listen port is a raw TCP forward. It is not a SOCKS listener of its own. If target is socks, the application speaks SOCKS on that port and the handshake is answered by the far service.
  • Lab use without an NS delegation, by sending the same queries straight at the VPS.

How a query reaches the VPS

The server listens for ordinary UDP DNS and is authoritative for domain. Each query name is a fresh long subdomain of that domain. The labels hide one encrypted blob. The answer is encrypted the same way: one TXT record, or a list of AAAA or A records when the client asked for those. Anyone who can read the packet still sees DNS.

udp and direct are mutually exclusive.

  • udp — the client sends the query to a recursive resolver (8.8.8.8:53, the ISP resolver, or another resolver that still recurses). The client does not dial the VPS and does not walk the hierarchy itself. The resolver does: root, the TLD, then the NS record for domain, which must point at the VPS. The client needs domain, enc-key, and the resolver address.
  • direct — the client sends those same UDP queries straight to the VPS. There is no resolver and no NS delegation. Use this in a lab, and only when the network allows UDP to the VPS address. A network that allows DNS only toward its own resolver will drop it.

DoH and DoT are not transports here. Both are TCP. On a network that blocks TCP they would not start, and they are not implemented for this tunnel.

Example JSON (forward, via a resolver)

{
  "server": [
    { "type": "socks", "listen": "127.0.0.1:0", "tag": "exit" },
    {
      "type": "dns",
      "listen": ":53",
      "domain": "t.example.com",
      "enc-key": "shared-secret",
      "mtu": 1232,
      "target": "exit"
    }
  ],
  "client": [
    {
      "type": "dns",
      "listen": "127.0.0.1:7000",
      "domain": "t.example.com",
      "enc-key": "shared-secret",
      "udp": "8.8.8.8:53"
    }
  ]
}

An application that connects to 127.0.0.1:7000 is one TCP stream to the service tagged exit. Point a browser’s SOCKS proxy at that port only when exit is a socks service. The bytes on 7000 are copied through; the dns client does not speak SOCKS itself.

Lab, no NS delegation. The client uses direct instead of udp:

{
  "server": [
    { "type": "external", "listen": "127.0.0.1:22", "tag": "ssh" },
    {
      "type": "dns",
      "listen": ":53",
      "domain": "t.example.com",
      "enc-key": "shared-secret",
      "target": "ssh"
    }
  ],
  "client": [
    {
      "type": "dns",
      "listen": "127.0.0.1:2222",
      "domain": "t.example.com",
      "enc-key": "shared-secret",
      "direct": "203.0.113.10:53"
    }
  ]
}

ssh -p 2222 127.0.0.1 then reaches 127.0.0.1:22 on the VPS. Queries go to 203.0.113.10:53 and never ask a public resolver.

Keys and what DPI sees

Both sides set the same enc-key. PT Proxy derives two keys from it: the Noise static key for the session, and a ChaCha20 key for the query blob and the answer. Each blob is an 8-byte nonce, the ciphertext, and a 4-byte tag. Encryption is always on. A query name is base32 of that blob, then the configured domain. The answer is the same cipher. With qtype txt that is one TXT record. With aaaa or a it is split across address records. A resolver, and any DPI that reads the DNS message, cannot recover the client id or the TCP payload. They can still see the query type and that this host is sending many long names under one zone.

On the udp path the packet toward the resolver is plaintext DNS. On the direct path that same DNS packet goes to the VPS address, so the path can also associate the flow with the server IP.

How it works

The client encodes one KCP packet into each query. That packet is as large as the domain allows, unless packet-size sets a smaller one. The server decrypts the name, feeds KCP, and completes Noise and smux. Each smux stream dials target and copies bytes both ways. Downstream KCP packets are bundled into the answer until mtu. An aaaa or a client gets a smaller server MTU so each segment still fits in one reply. Polling continues while the session is idle so the server has a query to answer. The name stays a subdomain of domain because that suffix is what the recursive resolver uses to find the authoritative server.
