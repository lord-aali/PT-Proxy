DPI (HTTP/HTTPS tunnel)

Carries TCP and UDP inside encrypted HTTP(S) requests so the session looks like ordinary web traffic. Good when only HTTPS (or a specific hostname) is allowed. Domain fronting: dial IP in address, set sni and front-host to the allowed name.

Capabilities

  • Forward and reverse (TCP + UDP)
  • HTTP and/or HTTPS listeners; TLS from files, ACME, or a self-signed cert
  • Optional redirect for normal browsers hitting the same port
  • Two uplinks: many short POSTs (post-async, works behind CDNs) or one long upload + download (stream, typically faster on a direct server)

Config

Server: http / https, enc-key, TLS options, optional redirect, optional target.

Client: address URL, listen, enc-key, optional sni, front-host, insecure, uplink, reverse-tag. Reverse uses stream.

How it works

Each flow has a connID. Messages are a 10-byte header (version, type, connID, payload length) then payload, encrypted. Stream uplink frames are length-prefixed. Paths such as /.well-known/cdn-cache/, /api/v2/upload, /api/v2/stream, and /download/session/ carry the tunnel.

MsgIDCapability
Connect0x01Open a flow; server dials target when set
Data / Close0x02 / 0x03Bytes and teardown
UDP0x04 / 0x05Datagrams (skipped for http targets)
ReverseBind / ReverseOpen0x07 / 0x09Publish a port on the server; incoming TCP becomes a new connID

Forward: client binds TCP+UDP on listen, each TCP accept is a Connect, UDP shares one assoc. Reverse: client sends ReverseBind; server binds and pushes ReverseOpen; client dials the tagged service.
