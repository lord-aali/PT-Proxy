Forward and reverse

Every camouflage tunnel can carry TCP streams and UDP datagrams (UDP is framed inside the tunnel). What you attach at each end is a tagged service: socks, http, or external.

Forward

The service runs beside the tunnel server. The client binds listen locally. Applications connect to that port; each TCP connection and each UDP packet is carried to the service named by the server’s target.

App  --TCP/UDP-->  client listen  --tunnel-->  server  --dial-->  tagged service

If that service is SOCKS5, the app speaks SOCKS on the client port. If it is SSH, the app speaks SSH. The tunnel copies bytes.

Config: service + tunnel with target on the server machine; tunnel client with address and local listen.

Reverse

The service runs beside the tunnel client (listed under that process’s server array). The public tunnel has no target. The client sets reverse-tag and listen — listen is the address to publish on the tunnel server.

Peer  --TCP/UDP-->  server bind (client.listen)  --tunnel-->  client  --dial-->  reverse-tag service

The client asks the server to bind that address (TCP and UDP). The server replies with the real bound address (useful when the port was 0). Each accepted TCP connection becomes a stream to the client, which dials the tagged service. UDP uses a datagram stream and remembers the last peer so replies return correctly.

UDP

On the wire, tunnels are reliable streams. UDP is encapsulated (address + payload). SOCKS5 UDP ASSOCIATE uses the same port as TCP. HTTP CONNECT is TCP-only.
